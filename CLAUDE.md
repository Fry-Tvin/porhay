# Порхай — пересборка сайта с Тильды

Развлекательный центр во Владивостоке, ул. Державина 23. Задача: перенести сайт
с Тильды на свою вёрстку, **сохранив дизайн один в один** — владелице он нравится,
менять его нельзя.

## Что где лежит

| Папка | Что это |
|---|---|
| `porhai-eds/` | Исходный экспорт с Тильды. **Только для чтения** — эталон и источник картинок. |
| `porhai-new/` | Новая вёрстка. Здесь идёт вся работа. |
| `porhai-new/spec/` | Спецификация вёрстки, снятая с экспорта: координаты, стили, тексты по всем брейкпоинтам. |
| `porhai-new/assets/` | `style.css`, `img/` (пережатые картинки), `fonts/` (Evolventa). |

## Инструменты

Запускать из `porhai-new/`:

```bash
python extract_spec.py      # экспорт Тильды -> spec/*.json (уже снято, повторять не нужно)
python optimize_images.py   # картинки из экспорта -> assets/img/ в WebP
python build.py             # spec + шаблоны -> index.html
python make_standalone.py   # автономный файл для показа без сервера
python make_artifact.py     # файл для публикации по ссылке
```

Локальный просмотр — из корня `Таплинк/`:
`python -m http.server 8777`, дальше `/porhai-new/index.html` и `/porhai-eds/page34664661.html` для сверки.

## Главное правило

**Дизайн не трогаем.** Никаких «улучшу отступы», «поправлю цвет», «этот шрифт лучше».
Совпадение проверяется числами, а не на глаз. Допуск — 2 px.

Менять можно и нужно только то, что перечислено в разделе
«Что из аудита входит в пересборку, а что нет», группы A и B.

## Как читать спеку

`spec/page34664661.json` — массив блоков в порядке следования. У блока:

- `id` — идентификатор блока в Тильде (`rec…`), по нему же ищется оригинал;
- `kind` — что это за блок по-русски;
- `height` — высота артборда по брейкпоинтам;
- `background` — фон;
- `elements` — элементы зеро-блока с `geometry`, `styles`, `text`, `image`;
- `texts` / `images` — для обычных блоков Тильды, у которых нет свободного позиционирования.

### Брейкпоинты — читать внимательно

Ключи в `geometry` и `styles` — это `max-width` медиазапросов Тильды:

| Ключ | Когда применяется | Что там |
|---|---|---|
| `base` | ≥ 1920px | Исходный макет. Координаты лежат **только здесь**. |
| `1919` | 1200–1919px | **Основной десктоп.** Здесь верные кегли. |
| `1199` | 960–1199px | Планшет. |
| `959` | 640–959px | Крупный телефон. |
| `639` | 480–639px | Телефон. |
| `479` | < 480px | Узкий телефон. |

Две ловушки:

1. **Кегли брать из `1919`, а не из `base`.** В `base` H1 — 68px, но на реальном десктопе он 58px.
2. **Координаты из `base` нельзя подставлять напрямую.** Они заданы в системе координат
   макета Тильды и на странице пересчитываются. Пользуйтесь ими для понимания
   композиции и пропорций, а точные значения снимайте замером (см. ниже).

## Порядок работы над секцией

1. **Прочитать спеку блока** — состав, тексты, картинки, фон, высота.
2. **Снять эталонные координаты с оригинала.** Открыть
   `http://localhost:8777/porhai-eds/page34664661.html` и выполнить в консоли:

   ```js
   (() => {
     const rec = document.getElementById('recNNNNNN');
     const art = rec.querySelector('.t396__artboard') || rec;
     const ar = art.getBoundingClientRect();
     return [...rec.querySelectorAll('.t396__elem')].map(e => {
       const a = e.querySelector('.tn-atom'), s = a ? getComputedStyle(a) : {}, r = e.getBoundingClientRect();
       const im = e.querySelector('img');
       return {t: e.getAttribute('data-elem-type'),
         x: Math.round(r.left - ar.left), y: Math.round(r.top - ar.top),
         w: Math.round(r.width), h: Math.round(r.height),
         txt: (a && a.innerText || '').trim().slice(0, 60),
         img: im ? (im.getAttribute('data-original') || im.src || '').split('/').pop() : null,
         bgImg: s.backgroundImage !== 'none' ? s.backgroundImage.split('/').pop() : null,
         fs: s.fontSize, fw: s.fontWeight, lh: s.lineHeight, color: s.color,
         bg: s.backgroundColor !== 'rgba(0, 0, 0, 0)' ? s.backgroundColor : null,
         br: s.borderRadius !== '0px' ? s.borderRadius : null,
         tr: s.transform !== 'none' ? s.transform : null};
     });
   })()
   ```

   Замер делать при ширине артборда **1265px** — это тот же режим, в котором свёрстано
   уже готовое. Картинки лениво подгружаются, поэтому перед замером прокрутить до блока.

   **Важно про песочницу.** Сеть в этом окружении блокирует `static.tildacdn.com`,
   поэтому `Evolventa` на `porhai-eds` не грузится и браузер молча подставляет
   Arial — размеры текста (высота строк, перенос по словам) будут неверны, хотя
   расположение нетекстовых элементов (иконки, отступы, картинки) не пострадает.
   Если меряете что-то, зависящее от текста (перенос строк, высота блока с текстом),
   подменяйте шрифт через перехват запроса на локальный файл, иначе цифры соврут:
   ```js
   await page.route('**/Evolventa-Regular.woff', r => r.fulfill({ path: 'porhai-new/assets/fonts/Evolventa-Regular.woff' }));
   await page.route('**/Evolventa-Bold.woff', r => r.fulfill({ path: 'porhai-new/assets/fonts/Evolventa-Bold.woff' }));
   ```
   Playwright с Chromium в песочнице уже есть (`/opt/pw-browsers`, глобальный npm-пакет
   `playwright` в `/opt/node22/lib/node_modules`) — им и снимать замеры вместо консоли браузера.

   Та же сеть блокирует и карты (`yandex.ru/map-widget` отвечает 403 через прокси
   песочницы) — блок «Контакты» использует Яндекс-виджет с адресом в query-параметре,
   в песочнице рендерится плейсхолдером-«битой картинкой», это ожидаемо и не баг.
   Проверять реальную отрисовку карты можно только вне песочницы.

3. **Сверстать секцию** нормальным потоком: flex или grid, без абсолютного
   позиционирования содержимого. Абсолютно позиционируется только декор
   (кляксы, мелкие картинки) — он и в оригинале декор.
4. **Добавить картинки** в `DISPLAY_WIDTH` в `optimize_images.py` с шириной отображения
   и прогнать пережатие.
5. **Сверить числа** — открыть свою страницу и снять те же координаты. Расхождение
   больше 2px — дорабатывать. Сверять обязательно: высоту секции, позиции заголовка,
   подзаголовка и основного содержимого, кегли, цвета, радиусы.
6. **Проверить мобильную** — ширина 375. Требования: нет горизонтальной прокрутки
   (`document.documentElement.scrollWidth === clientWidth`), нет кликабельных элементов
   мельче 40×40, нет битых картинок.
7. **Пересобрать** — `python build.py`, при необходимости `make_artifact.py`.

## Что из аудита входит в пересборку, а что нет

Аудит дал 30 находок. Они делятся на четыре группы, и смешивать их нельзя.

### A. Делается молча — внешний вид не меняется

Никакого согласования не требуется, это просто часть качественной вёрстки.

- `lang="ru"`, семантика: `h1`/`h2`/`h3`, `nav`, `main`, `figure`, `figcaption`.
- Две битые «фигмовские» кляксы — локальные копии подставлены в `build.py`, словарь `BIT`.
- Картинки только WebP, под реальный размер отображения ×2.
- Шрифт Evolventa лежит локально, без обращения к CDN Тильды.
- Разметка LocalBusiness и FAQPage — при вёрстке контактов и FAQ.
- Цели Метрики и пиксель VK — при подключении аналитики.
- Чистые адреса страниц без зависимости от `.htaccess`.
- Кликабельные элементы не мельче 40×40 на мобильной.

### B. Обязательно по закону — добавляет видимые элементы

Без этого сайт нельзя публиковать и нельзя рекламировать. Элементы новые, поэтому
делать их строго в фирменном стиле: те же цвета, шрифт и скругления, минимальный размер.

- Чекбокс согласия на обработку персональных данных в каждой форме.
- Страница политики конфиденциальности и ссылка на неё в подвале.
- Реквизиты организации в подвале.
- Баннер согласия на cookie.

### C. Заблокировано на владелице — не выдумывать

- Актуальные цены. В экспорте они за 2023 год. Переносить как есть, вести список того,
  что требует обновления, и показывать заказчику.
- Тексты вроде «Выпускные 2023 не за горами» — пометить, но не сочинять замену.
- Реквизиты, ИНН, форма собственности.
- Что делать с партнёрами в Instagram.
- Отзывы в 2ГИС и на Яндекс.Картах.

Исключение: замазать номер телефона клиента на скриншоте отзыва
(`images/tild3139-6336-4961-b439-303832396662__photo_2023-02-19_16-.png`) можно и нужно
сразу — это утечка персональных данных третьего лица.

### D. За рамками пересборки — отдельный этап после переезда

Это уже изменение дизайна и логики, а не перенос. Сюда **не лезем**, пока идёт вёрстка.

- Календарь свободных дат.
- Поля «дата» и «повод» в форме заявки.
- Вилка цен или калькулятор на странице корпоративов.
- Подарочные сертификаты.
- Сбор базы и напоминания о дне рождения.
- Кликабельный телефон на первом экране мобильной версии.
- Дублирование текстов отзывов рядом со скриншотами.
- Блок «как добраться», возрастные ограничения.

Почему отдельно: если менять дизайн одновременно с переносом, потом невозможно понять,
от чего изменились заявки — от новой скорости или от нового блока. И владелица теряет
тот сайт, который ей нравится, не успев его увидеть на новом месте.

## Чего не делать

- Не менять композицию, цвета, шрифты, размеры.
- Не «причёсывать» тексты — переносить дословно, включая опечатки вроде «Cтильные»
  (там латинская C) и «лишний траты». Исправлять только по согласованию.
- Не тащить jQuery и никакие библиотеки. Сейчас на странице 0,3 КБ скрипта, так и держать.
- Не трогать `porhai-eds/` — это эталон.

## Правки по итогам первой мобильной проверки (главная)

Заказчик проверил главную на телефоне и прислал 22 пункта. Все внесены,
сверены и проверены (0 JS-ошибок, 0 битых картинок, 0 горизонтальной
прокрутки на всех 11 страницах после правок):

- **Лента-разделитель на мобильной** — главная находка: на мобильной
  оригинал НЕ пересчитывает координаты шариков/чёрточек в % ширины экрана,
  холст остаётся физически в масштабе десктопа и просто обрезается
  viewport'ом (`overflow-x:clip` на `html` уже стоял) — в видимом окне
  остаётся 6–7 шариков, а не все 16 сразу. У нас `.band__inner` растягивался
  на 100% контейнера, поэтому все 16 шариков и 15 чёрточек сжимались в
  375px и наезжали друг на друга. Фикс — вернуть холсту фиксированную
  ширину `--stage` и центровать, как на десктопе (`@media (max-width:1000px)`).
  Заодно убран отдельный мобильный размер шарика (76px) — замер показал,
  что на мобильной шарик почти не отличается от десктопных 109px.
- **Шапка на мобильной** — оригинал не получает мятный фон после
  прокрутки на мобильной (в отличие от десктопа, где `is-stuck` работает
  штатно) — подтверждено скроллом до 1500/3000/6000px на оригинале.
  `.header.is-stuck` на мобильной глушится до `background:transparent`.
- **Межстрочный интервал заголовков секций** — `.section__title` на
  мобильной шрины (32px) наследовал десктопный `line-height:64px`
  (не переопределялся), получалось соотношение 2:1. Замер оригинала на
  375px даёт line-height ≈ font-size (1.0–1.2). Поставлено `line-height:1.15` —
  чинит разом все 6 заголовков, на которые жаловался заказчик («Мы делаем
  ваш праздник ярче», «Праздники под ключ», «Для организованных групп»,
  «Незабываемые эмоции», «Скидки от партнёров», «Отвечаем на ваши вопросы»).
- **Рамки карточек (тёмно-бирюзовая/жёлтая обводки) — дрейф добавляли и
  откатили.** В оригинале у них есть scroll-driven анимация (замерено в
  спеке: teal mx:-10, yellow mx:+10), сначала добавил `data-drift` (тот же
  приём, что у ленты и hero-иллюстрации) на `.card__frame` и `.tariff__frame`.
  Заказчик прислал скриншот — фон карточки вылезал за пределы рамки
  (розовый фон торчал по углам). Причина: наш `paint()` считает дрейф как
  **непрерывную** функцию текущего положения элемента в вьюпорте (синус-волна,
  максимум когда элемент по центру экрана) — подходит для ленты и
  hero-иллюстрации, у которых нет «контейнера», из которого можно вылезти.
  А в спеке этих рамок keyframes другие: `di` (длительность каждого сегмента
  в мс) описывает **разовую** анимацию «появился в зоне видимости → качнулся
  → вернулся в mx:0 и застыл», а не непрерывный дрейф, привязанный к
  прокрутке. Наш движок разового появления не умеет, поэтому рамка вместо
  «качнулась один раз и легла на место» весь скролл держится на максимальном
  смещении (±10px), пока карточка в середине экрана — ровно там, где
  пользователь её и читает. `data-drift` с `.card__frame`/`.tariff__frame`
  убран, рамки снова статичны. Разовую scroll-in-анимацию для них можно
  сделать отдельно через IntersectionObserver + Web Animations API (как уже
  сделано для мерцания мелкого декора, `[data-twinkle]`), но это отдельная
  задача, не расширение текущего `data-drift`.
- **Рамка тарифной карточки не тянулась по высоте (после отката дрейфа
  осталась вторая, более старая причина «кривизны»).** `.tariff__frame`
  рисовалась картинкой из экспорта — SVG с зашитыми пропорциями
  (1496×2161), ширина задавалась в процентах, а высота считалась от
  собственного соотношения сторон SVG, а не от высоты карточки. На
  десктопе карточка ниже пропорциональной высоты рамки, поэтому рамка
  выходила чуть больше и всё выглядело правильно; на мобильной текст
  переносится сильнее, карточка вырастала до 543px против 511px у рамки —
  и розовый фон карточки торчал снизу из-под рамки. Внутри SVG лежит
  обычный `<rect>` со скруглением и обводкой 2px, повёрнутый матрицей,
  так что рамка переписана на CSS (`border` + `border-radius` +
  `transform: rotate`): углы (+1° / −1,105°) и радиус (35px) вычислены
  из матрицы SVG, вид совпадает с оригиналом, но теперь тянется под любую
  высоту карточки. Проверено скриптом по всем 11 страницам на 375 и
  1265px: рамка нигде не короче своей карточки.
  У `.card__frame` (главная, «Мы делаем ваш праздник ярче») той же
  проблемы нет и картинка оставлена: там высота карточки жёстко задана
  через `aspect-ratio` у `.card__photo`, поэтому пропорции SVG и карточки
  всегда совпадают.
- **Плотность посадки рамки и разовое покачивание — доделано по просьбе
  заказчика.** После перехода на CSS-бордер отступ был −10px, и вокруг
  карточки читалась белая полоса. Отступ ужат до −5px: это самый плотный
  вариант, при котором рамка нигде не заезжает на карточку, потому что
  поворот на 1° уводит верхний и нижний углы по горизонтали на
  H/2·sin(1°) ≈ 4,7px. В итоге рамка в одном углу касается края карточки,
  в противоположном отходит на ~10px — «нарисованная от руки» посадка.
  Дрейф вернули, но правильным приёмом: не `data-drift` (непрерывная
  синус-волна от положения в вьюпорте, из-за которой рамка и застревала
  на максимальном смещении), а разовая анимация по `IntersectionObserver`
  + Web Animations API — ровно как keyframes оригинала (di 200/200/170мс,
  mx 0 → ±10 → 0): появилась → качнулась → застыла. Атрибут `data-swing`,
  пункт 2b в `PAGE_SCRIPT`. Поворот вынесен из `transform` в отдельное
  свойство `rotate`, а анимируется `translate`, поэтому они не затирают
  друг друга.
- **Лента-разделитель: вариант Б — своя раскладка, а не отражённый А.**
  `band(flip=True)` строился из тех же данных формулой
  (`y → −y+6`, `rot → rot+180`). Замер оригинала показал, что это неверно:
  у перевёрнутой ленты (rec572370702) и свои координаты шариков, и свои
  углы чёрточек (90°, −135°, −90°, 81°, 135°…), а не «те же плюс 180».
  Из-за формулы часть чёрточек висела криво, отрывалась от шариков и
  налезала друг на друга — заказчик разобрал это по номерам. Добавлены
  `BUBBLES_FLIP` и `CONFETTI_FLIP`, снятые замером при 1265px; `band()`
  выбирает набор по флагу. Дрейф для варианта Б переиспользован из А по
  порядку — в экспорте он свой, но той же амплитуды (21–45px), а на
  статичную раскладку не влияет.
- **Стрелка между шагами на мобильной** — должна быть вертикальной
  (сверху вниз), а не горизонтальной. CSS `transform:rotate(90deg)` уже
  стоял, но `position:static` без `display:block` вернул `<span>` к
  инлайновому поведению, где `width` не работает — рамка рисовалась в
  натуральную ширину и визуально не поворачивалась. Добавлен
  `display:block` в мобильном оверрайде.
- **Стрелки слайдера отзывов смотрели внутрь, а не наружу** — `scaleX(-1)`
  был на `--next`, а не на `--prev`; после поворота prev(слева) показывал
  «→», next(справа) — «←». Флип переставлен на `--prev`.
- **Слайдер отзывов терял синхронизацию через 5–7 карточек** — стрелки
  скроллили на `clientWidth * 0.8` (произвольная доля ширины контейнера),
  никак не привязанную к реальной ширине карточки+gap (`scroll-snap-type:
  x proximity` в такой ситуации не подтягивает к ближайшей карточке, если
  промах большой). Шаг переписан на точную ширину одной карточки
  (`img.getBoundingClientRect().width + gap`), snap-type — на `mandatory`.
  Проверено скриптом: после 8 кликов подряд смещение от края карточки — 0px.
  Тот же паттерн (`.slider__track`, /razovoe и др.) был устроен иначе
  (`flex:0 0 100%`, без gap) и не был затронут багом.
- **Подпись карточки** — по прямой просьбе заказчика (не по замеру
  оригинала — сознательное отступление от дизайн-системы ради
  читаемости на фото): 17px/400 → 19px/700 на мобильной.
- **Бассейн «Попкорн» переименован в «Пляж»** по всему сайту (3 места в
  build.py) + убрано фото жёлтого бассейна из галереи «Незабываемые
  эмоции» (замена появится, когда пришлют новое фото).
- **Галерея «Незабываемые эмоции» — плитки одного размера** вместо
  разных, как в оригинале (там Тильдовский T979 — justified-галерея,
  JS раскладывает фото по строкам с шириной под пропорции кадра;
  тащить для этого библиотеку не стали). Прибито по факту: у альбомных
  кадров общая пропорция ~3:2, у портретных ~2:3 — сделана CSS grid
  (`grid-auto-flow:dense`, `--wide`/`--tall` варианты плитки) без JS.
- **Тарифная карточка «Праздники под ключ» на мобильной** — второе
  (маленькое) фото заканчивалось на 238px (top:84+высота 154), а текст
  начинался с padding-top:210px — фото перекрывало заголовок «День
  рождения». Отступ увеличен до 250px.
- **Цена «День рождения» на главной** — добавлен суффикс «/3 часа» вслед
  за «от 16 500 ₽», как в оригинале (был потерян при переносе).
- **Лого «Весёлый пингвин»** — исходно был подставлен `frame_3.jpg` без
  альфа-канала (показывался на белом квадрате вместо прозрачного круга,
  как у остальных 5 партнёров). В экспорте нашлась копия того же лого
  в `.png` с настоящей прозрачностью (тот же `frame_3`, другой tild-хеш) —
  переключили на неё. Затронуло все страницы, где переиспользуется общий
  список `PARTNERS` (главная + 3 страницы аренды залов).
- **ВладФуршет и Café Tree убраны из плитки партнёров на главной** — по
  просьбе заказчика показываем только тех, у кого есть реальное лого,
  текстовые заглушки временно скрыты (на странице `/partner`, полный
  список, — оставлены, та страница ждёт своего раунда проверки).
- **Качество фото на мобильной** — расследование показало реальную
  причину: retina-запас в `optimize_images.py` был ×2, но многие крупные
  фото (карточки, слайдер отзывов, галерея) на мобильной рендерятся

  хватало и фото слегка мылило. Retina-запас поднят до ×3, все картинки
  пережаты заново (`assets/img/` пересобран с нуля, 0 пропущенных).
  Заодно поправлена собственная ошибка в новых записях для галереи
  (её DISPLAY_WIDTH был задан уже удвоенным вручную — задвоение с
  автоматическим ×RETINA в скрипте, из-за чего фото были явно крупнее
  необходимого).

Другие 11 страниц ещё не проверялись на этом раунде — заказчик
проверяет по одной странице за раз, следующий раунд начнётся, когда

## Правки по итогам проверки /razovoe

- **Стрелки слайдера смотрели друг на друга** — тот же баг, что чинили
  в `.reviews__arrow` на главной, но в другом компоненте (`.slider__arrow`,

  стрелка тоже смотрела вправо (внутрь), справа — влево (тоже внутрь).

  (denrozhdeniya, vypusknye, korporativ, whiteroom/loftbox/combo), почему
  не поймали раньше при чистке главной — недосмотр, не проверил остальные

  кадры (замерено на живой странице: 4.97с и 4.84с между переключениями,
  т.е. интервал ~5с). У нас было только по клику. Добавлен `setInterval`

- **Кружки-иконки в «Что включено» увеличены** — 140px это 1:1 с оригиналом

  (мобильная — 140px, было 110px). Сознательное отступление от дизайна,
  не ошибка переноса.

  и никогда не переопубликовывался — заказчик смотрел на старую версию.
  Проверено точным сравнением с оригиналом (с ожиданием окончания
  smooth-scroll перед замером, а не сразу после клика) — расхождений нет.
- **Блок со скидкой оформлен как настоящая цитата (T090), а не как
  центрированный абзац.** В оригинале это левоориентированная колонка
  (10 из 12 колонок сетки Тильды, отступ слева 1 колонка) с чертой сверху
  (`border-top`) и фигурной чертой снизу — обычный SVG-polygon в виде
  черты с «хвостиком»-флажком, указывающим на аватар автора. Раньше текст
  и подпись просто центрировались без единой линии — визуально другая
  композиция, хотя кегли и цвета совпадали. Переписано на `.quote__inner`

  Не трогать данные `CONFETTI_FLIP`/`BUBBLES_FLIP` без точных номеров —
  редактирование вслепую уже один раз ломало компоновку.
- **Нашлась и исправлена настоящая причина «съехавших полосок» — неверная
  форма кривой дрейфа, а не данные конкретных полосок.** Пронумерованные
  референсы всегда снимались с обнулённым `data-drift`, то есть показывали
  идеальный «покой», которого реальный посетитель на самом деле никогда
  не видит: `paint()` пересчитывает дрейф на каждый скролл. В спеке
  (`animation.scroll.keyframes` у элементов конфетти) — Тильдовская
  scroll-анимация всего из двух кейфреймов (`di:0→mx:0,ro:0` и
  `di:100→mx,ro`), то есть **линейная** интерполяция по проценту
  прохождения элемента через экран. В коде вместо этого стояла
  `Math.sin(p * Math.PI)` — волна с пиком ровно посередине экрана, из-за
  которой дрейф достигал 100% именно тогда, когда лента оказывалась по
  центру экрана — а это самый частый момент, когда пользователь
  останавливается и вообще смотрит на неё (там же обычно текст, который
  он в этот момент читает). В оригинале в этой точке дрейф — только
  около половины хода. Заменено на `Math.max(0, Math.min(1, p))` —
  линейная, как в кейфреймах. Проверено скриншотом в той же самой точке
  скролла (лента по центру вьюпорта) до и после — полоски перестали
  «улетать» от шариков. Правка в одном месте (`paint()` в `PAGE_SCRIPT`)
  общая для всех `data-drift` элементов сайта — обеих лент и hero-
  иллюстрации на главной.

## Правки 23.08.2026: настоящая причина «трэша» с полосками (вариант Б) и деплой на Pages

- **Найдена реальная причина «трэша» по полоскам на живом сайте (не то же
  самое, что баг с шариками из прошлого раунда).** Заказчик открыл сайт
  на своём ПК и увидел, что чёрточки на ленте прыгают в стороны без всякой
  связи с шариком под ними. Скриншоты рест-состояния (без скролла) при
  этом выглядели нормально — расхождение объясняется тем, что баг был
  именно в анимации, а не в статичной раскладке. Причина: при сборке
  `CONFETTI_FLIP` в прошлом раунде x/y (позиция) и mx/my/ro (анимация из
  `keyframes`) были сняты как два отдельных списка и склеены по индексу
  (`zip`) без проверки, что элемент №N в одном списке — это тот же
  элемент №N в другом. Тильда в spec не гарантирует одинаковый порядок
  для геометрии и для анимации одного и того же элемента — в итоге
  чёрточка на одной позиции получала анимацию совсем другого элемента.
  На скриншоте покоя это незаметно (файл на месте, цифры похожи), а при
  реальном скролле чёрточка улетает не в ту сторону.
- **Исправлено пересъёмкой по `data-elem-id`, а не по индексу.** На живом
  оригинале (`page34664661.html`, `rec572370702`, 1265px,
  `prefers-reduced-motion` — чтобы Тильда не крутила анимацию во время
  замера) для каждой чёрточки взяты её `data-elem-id`, позиция и базовый
  поворот, а её же mx/my/ro найдены в spec ПО ТОМУ ЖЕ id. Так каждая
  чёрточка гарантированно двигается своими собственными цифрами, а не
  чужими. Заодно на полотне этой ленты нашлось 33 картинки-чёрточки, а не
  32/16 — часть лишних по краям либо буквально невидимы (`opacity:0` у
  атома — мёртвый черновой элемент), либо давали нестабильные координаты
  между повторными замерами; оставлены только 15 чисто и одинаково
  воспроизводимых элементов (было 16, но с ложными данными). Проверено
  прямым сравнением скриншотов покоя оригинал/наш вариант — совпадение
  пиксель в пиксель по позиции каждой из 15 чёрточек.
- **404 на порхай.рф — GitHub Pages брал файлы из корня репозитория, а
  сайт лежит в `porhai-new/`.** В корне `main` — только `porhai-eds/`
  (эталон, не публикуется), `porhai-new/` (рабочая вёрстка) и служебные

  `.github/workflows/deploy-pages.yml` — при пуше в `main` собирает

  Source в Settings → Pages переключён на «GitHub Actions» (было «Deploy
  from a branch», физически смотрело в корень и не находило `index.html`).
- **Приём заявок с форм — решено использовать амоCRM напрямую, без
